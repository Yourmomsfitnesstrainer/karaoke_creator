# Измерение таймингов на локальном корпусе

Синтетические проверки рендера и акустические измерения на песнях решают разные задачи. Проценты «Сопоставление текста» не являются точностью времени.

## Синтетическая проверка

В окружении с dev-зависимостями, NumPy и FFmpeg/libass:

```bash
.venv/bin/python -m pytest
.venv/bin/python scripts/verify_render_timing.py --baseline-ref 350088c
.venv/bin/python scripts/verify_timing_faults.py
```

Первый скрипт сохраняет MP4, ASS, WAV и измерения B0/B1/B2 под `output/timing-verification`. Он использует исходные генератор ASS и renderer из указанного Git-коммита. Акустические границы всех этих вариантов одинаковы. Второй скрипт вносит семь дефектов во временную копию исходников, проверяет падение тестов и восстановление, сохраняет точные diff и логи. Рабочий checkout он не меняет. Для одной пробы используйте `--probe`, например `--probe stanza-boundary-ignored`.

## Работа без эталонов

По решению пользователя дальнейшая разработка продолжается на локальных песнях без ручной разметки. [Результаты и сохранённый кандидат](timing-stability-report.md).

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 .venv/bin/python scripts/check_timing_stability.py \
  --audio /path/to/vocals.wav --lyrics /path/to/lyrics.txt \
  --output output/stability-new --language ru --asr-model medium \
  --models bond005/wav2vec2-base-ru jonatasgrosman/wav2vec2-large-xlsr-53-russian \
  --contexts 0.3
```

Runner распознаёт исходный звук один раз, затем проверяет уточнение и mapping при фиксированной ASR-сетке: добавляет 750 мс тишины, уменьшает амплитуду вдвое и повторяет аудио с паузой 1 с. Время ASR для преобразований переносится по известному смещению. Это изолирует устойчивость уточнения и привязки текста; устойчивость повторного распознавания таким способом не измеряется.

`report.json` сохраняет версии, хеши, текстовое покрытие, происхождение таймингов и дельты каждого слова. `over_40ms` — счётчик изменений более 40 мс, не акустическая приёмка. Все слова, включая fallback, остаются в расчёте. Вставка тишины и повтор могут изменить контекст окон у начала/конца записи, поэтому выбросы требуют разбора по provenance. Значение `seconds` включает уточнение либо чтение его кеша и mapping; оно не является чистым временем инференса.

MP4 этого runner использует поданный звук. Для просмотра с музыкой в контрольном кандидате сохранены отдельные видео с исходной фонограммой. Понравившийся после просмотра вариант можно зафиксировать как контроль для будущих регрессий. Пока отзыв не получен, `human_review=pending`, `ground_truth=false`.

## Подготовка корпуса

Разделите песни на `tuning` и `acceptance` до настройки моделей, контекста и порогов. Одна песня не может присутствовать в обеих группах, даже под разными именами. Минимум: 5 песен, 15 фрагментов по 20–40 секунд и 500 различимых слов; для независимой приёмки — минимум 3 песни и 300 слов с однозначным началом.

Зафиксируйте первый/последний различимый звук основного вокала, неопределённость разметки и неоднозначные концы. Все времена абсолютные относительно **первого декодированного сэмпла оригинала**, не относительно начала фрагмента. `index` — индекс слова во всём очищенном TXT, начиная с нуля; он различает повторения припевов.

Для каждой песни сохраните:

- `analysis_audio`: фактический WAV для анализа (обычно `vocals.wav`).
- `lyrics`: окончательный TXT.
- `asr_json`: один файл `work/timing-cache/asr-<hash>.json`, общий для всех уточнителей.
- При наличии: `baseline_alignment` от исходного алгоритма на той же ASR-сетке и `baseline_asr_sha256` — SHA-256 именно этого файла ASR. Связь baseline с ASR декларирует автор корпуса; код дополнительно проверяет TXT и длительность. Старый результат с другой ASR-сеткой не является контролируемым baseline.

Манифест содержит относительные к себе пути. Ниже только пример структуры; сокращённая разметка не удовлетворяет минимуму корпуса:

```json
{
  "songs": [{
    "id": "song-01",
    "split": "tuning",
    "analysis_audio": "song-01/vocals.wav",
    "lyrics": "song-01/lyrics.txt",
    "asr_json": "song-01/asr.json",
    "fragments": [{
      "id": "verse-01",
      "start": 20.0,
      "end": 45.0,
      "words": [{
        "index": 18,
        "text": "Привет,",
        "start": 21.12,
        "end": 21.68,
        "uncertainty_ms": 20,
        "start_unambiguous": true,
        "end_unambiguous": true,
        "cases": ["pause", "sustain"]
      }]
    }]
  }]
}
```

Сохраняйте манифест и разметку до начала эксперимента. Runner пишет их хеши в отчёт; после правок эталона это уже другое измерение. Метки `cases` задаёт разметчик: например `repeat`, `quiet`, `rap`, `sustain`, `compound`, `overlap`.

## Сравнение моделей и окон

```bash
.venv/bin/python scripts/benchmark_timing.py \
  --corpus /path/to/corpus.json --output output/benchmark-tuning \
  --split tuning --contexts 0 0.3 0.6 \
  --models bond005/wav2vec2-base-ru jonatasgrosman/wav2vec2-large-xlsr-53-russian
```

Runner не запускает ASR или Demucs: все варианты используют один сохранённый ASR и один WAV. Он сверяет WAV с хешем входа ASR. Для необязательного третьего кандидата добавьте `bond005/wav2vec2-large-ru-golos`. Совместимость и качество этого кандидата в текущей работе не проверены.

По умолчанию используется score floor 0,05, помеченный `uncalibrated_sanity_floor`. Это только защита от явно плохого кандидата, **не откалиброванная вероятность точности**. На tuning-песнях сравните пороги отдельно для каждой модели. Сохраните выбранные значения в JSON, например `{"bond005/wav2vec2-base-ru": 0.05}`, и передайте `--score-thresholds /path/to/thresholds.json`. Пример не является рекомендацией порога. В основном приложении эти значения задаются через `alignment.score_thresholds` в YAML.

После фиксации модели, контекста и порогов запустите только выбранный вариант с `--split acceptance`. Не подбирайте параметры по независимой группе. Новая модель скачивается только при фактическом запуске соответствующего варианта.

## Интерпретация отчёта

`report.json` содержит общий результат, каждую песню, каждый `case`, статусы слов, покрытие, происхождение таймингов, настройки, хеши, ревизии доступных моделей и время. Если ревизия модели недоступна, она остаётся `null`.

Квантили используют nearest-rank. Пропавший, невалидный или подменённый текстовый токен получает бесконечную абсолютную ошибку внутри расчёта; в JSON это `null` со статусом ошибки. Такой токен остаётся в знаменателе. Валидные ASR/interpolated/approximate fallback участвуют в общей метрике. Signed bias считается по конечным предсказаниям с отдельным числом наблюдений. Неоднозначные концы исключаются только из метрики конца.

Порог приёмки: median start ≤80 мс, P90 start ≤150 мс, доля start-ошибок >250 мс ≤2%, |median signed start| ≤40 мс, P90 однозначных end ≤200 мс. При исходном P90 >150 мс требуется снижение минимум на 30%; иначе — отсутствие ухудшения общего P90. P90 отдельной песни не должен ухудшиться более чем на 20 мс.

Без достаточного корпуса результат — `insufficient_corpus`; без полного baseline или на tuning-группе приёмка не запускается. Эти проверки не заменяют контроль независимости песен и качества ручной разметки.
