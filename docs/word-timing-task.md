# ТЗ v1 — улучшение таймингов слов в караоке

Историческое ТЗ, составленное до реализации. Описание исходных проблем ниже относится к baseline `350088c`, а не к текущему коду. Результаты реализации и оставшиеся проблемы описаны в [итоговом отчёте](timing-stability-report.md).

## Контекст проекта

Репозиторий: `/Users/artembocarov/Documents/ChatGPT/karaoke_creator`.
Созданная ветка: `improve/word-timing-accuracy`, от `main`, базовый коммит `350088c`.
Подробное ТЗ: `.archcore/lyrics-timing/word-timing-accuracy.prd.md`.

ТЗ и этот файл сохраняются вместе с реализацией для истории требований.

Продукт — локальный Python-генератор: оригинальный MP3 + окончательный TXT → распознавание faster-whisper → уточнение WhisperX → сопоставление с TXT → ASS/libass → MP4. Есть CLI и FastAPI Web UI, опциональное отделение вокала Demucs. Основная платформа — Mac на Apple Silicon, без обязательной CUDA.

Перед изменениями прочитать AGENTS.md и относящиеся к задаче документы Archcore. Вести видимый план и сообщать о результатах проверок. Исследовать и исправлять только относящийся к таймингам код; посторонние изменения сохранять.

## Цель и приоритеты

После предыдущих улучшений и выбора тяжёлой ASR-модели результат стал лучше, но отдельные слова всё ещё расходятся с вокалом примерно на 200–300 мс. Ошибка разнонаправленная: некоторые слова раньше, другие позже. Точность важнее скорости; более длительная обработка допустима.

Граница слова определяется исполнением основного вокала: первый различимый звук — start, последний — end. Не привязывать слова механически к битам. Конкретный трек пользователь сейчас не предоставляет; это не мешает исправлять доказанные дефекты, но ограничивает проверку реальной точности.

## Что уже установлено

- Default подсветки −250 мс задан в config.yaml, config.py и Web. Он влияет на все слова одинаково и не исправляет локальные ошибки в обе стороны.
- Выбор medium/large-v3 меняет ASR-модель; русская модель уточнения остаётся `bond005/wav2vec2-base-ru`.
- WhisperX получает исходные ASR-окна без добавления контекста. Возможная обрезка звуков на границе окна требует эксперимента.
- Уточнение принимается по текстовому соответствию, а итоговая confidence сохраняется от ASR. Синтетически подтверждено: сдвиг на 200 мс при score уточнителя 0,01 принимается с итоговой confidence 0,99.
- Нормализация пересечений может сдвинуть начало слова на 300 мс; исходная граница и причина коррекции не сохраняются.
- Составные соответствия делятся по длинам токенов; это приблизительная внутренняя граница.
- ASS растягивает заливку слова на паузу до следующего. Также нужно проверить накопление округлений и обрезку отрицательного offset у начала файла.
- Показатель Alignment quality считает совпавшие слова, а не ошибку времени.
- Кеш alignment не включает версию алгоритма и хеш фактического WAV для анализа.

Это факты о коде и синтетических примерах, а не доказательство конкретной причины на песнях пользователя.

## Требования

### 1. Точный перенос JSON → ASS → MP4

- Предлагаемый default новых запусков — offset=0. Сохранить явные пользовательские значения и диапазон −1000…+1000 мс; старые конфигурации автоматически не переписывать.
- Заливка каждого слова идёт только от start до end. Во время паузы слово уже залито, следующее ещё ожидает start.
- Считать ASS-время от абсолютных границ, без накопления округлений длительностей.
- Обрезка события у нуля не перезапускает всю относительную последовательность слов. Переносы строк и preview не меняют время слов.
- Offset применяется один раз при рендере; canonical JSON и аудио не сдвигаются.
- Добавить явный offset override для CLI render; показывать эффективное значение в диагностике.

### 2. Улучшение акустических границ

- Сохранить recognition-first и глобальное монотонное сопоставление. Display-текст происходит только из TXT; все пользовательские слова сохраняются.
- Уточнять в ограниченных окнах с контекстом и проверкой временной принадлежности. Повторяющиеся слова не переносятся между припевами.
- Проверять конечность времён, длительность, границы аудио, порядок, отдельный score уточнителя и соседние якоря.
- Калибровать score для конкретной модели. Не смешивать его с confidence ASR и не использовать величину сдвига как единственный фильтр.
- При отклонённом уточнении сохранять ASR-границы и причину. При отсутствии соответствия сохранять отмеченную интерполяцию. Если совпадений нет совсем — понятная ошибка.
- Для составных соответствий использовать доступные акустические/символьные границы. Деление по длине текста маркировать приблизительным.
- Любую коррекцию пересечений сохранять с исходными временами и величиной изменения; не скрывать цепочки сдвигов.
- Сравнить текущую русскую модель с `jonatasgrosman/wav2vec2-large-xlsr-53-russian`; при необходимости проверить `bond005/wav2vec2-large-ru-golos`. Более тяжёлая модель рекомендуется только после измеренного выигрыша.

### 3. Диагностика, совместимость и кеш

- `lines[].words[].start/end` остаются единственными каноническими границами для render и ручных правок.
- Отдельно хранить исходные времена, кандидат уточнения, источник, оценки ASR/уточнения, причину fallback или коррекции. Эти поля не перезаписывают ручные правки при чтении.
- Различать уточнение по аудио, исходный ASR, приблизительное разделение, интерполяцию и ручные правки. В старых файлах неизвестные сведения не придумывать.
- Новая схема читает JSON 1/2. Повторный render не вызывает ML.
- Записывать фактические настройки, версии алгоритмов/моделей/пакетов, хеши входов и длительности стадий.
- Разделить кеш ASR и уточнения. Смена уточнителя пересчитывает нужную стадию; изменение оформления/offset сохраняет ML-кеш.
- Проверять общую временную шкалу оригинала, stem и конечного MP4, включая начало потока и resampling. Одинаковая длительность ещё не доказывает отсутствие сдвига.
- В Web назвать текстовую метрику «Сопоставление текста». Без эталона не показывать выдуманную точность в процентах или миллисекундах.

## Проверка и критерии готовности

Сначала доказать корректность рендера на синтетическом клипе с известными аудиомаркерами: проверить кадры и декодированное аудио. Допуск JSON → ASS: ≤10 мс без накопления; дополнительный допуск MP4: ≤1 кадра + 10 мс, около 43 мс при 30 fps.

Проверить паузы 300 мс, длинные строки с дробными временами, offset обоих знаков и обрезку у нуля, пересечения, распевы, составные соответствия, повторения, низкий score, fallback, совместимость JSON и инвалидирование кеша.

Реальная приёмка требует локального размеченного корпуса: минимум 5 песен, 15 фрагментов по 20–40 секунд, ≥500 различимых слов. Минимум 3 песни и 300 однозначно размеченных слов оставить для независимой приёмки; остальные — для настройки. Разделять по песням до подбора параметров.

Предлагаемые акустические пороги при offset=0:

- Медиана абсолютной ошибки начала ≤80 мс, P90 ≤150 мс.
- Доля ошибок начала >250 мс ≤2%.
- Абсолютная медиана signed error начала ≤40 мс.
- P90 ошибки конца для однозначных границ ≤200 мс.
- Если исходный P90 >150 мс, снизить его минимум на 30% и выполнить абсолютные пороги; иначе сохранить качество.
- Не ухудшить P90 начала отдельной приёмочной песни более чем на 20 мс.

Считать акустические ошибки по JSON без offset, визуальные — по MP4 относительно оригинального аудио. Не смешивать эти результаты. Использовать одинаковые ASR, аудио, TXT, VAD и корпус для сравнения уточнителей.

Базовые варианты: B0 — текущий код с −250 мс; B1 — тот же код с 0 мс; B2 — исправленный рендер той же ML-сетки с 0 мс; C — новое уточнение с исправленным рендером. Акустические времена B0/B1/B2 одинаковы.

Заранее зафиксировать эталонные точки и неопределённость разметки. Квантили — nearest-rank. Пропавшая/невалидная граница считается неудачей с бесконечной абсолютной ошибкой в расчёте, а не исключается; в JSON хранится статус ошибки. Валидные fallback включаются в общую метрику. Публиковать покрытие, результаты каждой песни и сложных случаев; signed bias считать по конечным предсказаниям.

Пороги пока не проверены на реальных песнях. Если корпуса нет, завершить доступные исправления и синтетические проверки, отдельно указать непроверенную акустическую приёмку. Не объявлять улучшение точности доказанным по unit-тестам.

3. Разделить кеш и проверить временную шкалу аудио.
4. Сравнить модели/окна и обработку составных соответствий на фиксированных данных.
5. Обновить существующую диагностику CLI/Web, README и контракты Archcore.
6. Предоставить отчёт: изменения, тесты, B0/B1/B2/C, реальные метрики при наличии корпуса и ограничения.
